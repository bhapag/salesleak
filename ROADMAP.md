# SalesLeak — Roadmap

Built in small, explicitly-approved phases. Nothing in a later phase starts until the user approves it. Everything runs locally until stated otherwise.

## Phase 1 — Foundation ✅ Done

Next.js + TypeScript + Tailwind scaffold, Prisma + SQLite with the full core schema (Company, User, Customer, Lead, Activity, Task, Quotation, QuotationItem, Product, Integration, Notification, AuditLog), realistic seed data for one fake Indian industrial company, and a basic dashboard proving the stack works end to end.

## Phase 2 — Lead Management ✅ Done

Production-quality Leads list (`/leads`) and Lead detail (`/leads/[id]`) pages: search, filters, sorting, empty/loading states, risk highlighting, and working actions (mark contacted, change status, assign salesperson, schedule follow-up, update next action, add note, mark Won, mark Lost with mandatory reason). Enforces the core rule — every active lead needs an owner, status, next action, and deadline, or it's flagged. Added `priority`, `product`, `quantity` to `Lead`. No integrations, no AI, no auth yet.

## Phase 3 — Quotation Management & Sales Leakage Dashboard ✅ Done

Quotations list (`/quotations`) and Quotation detail (`/quotations/[id]`) pages with the same quality bar as Phase 2's leads pages: search, filters (status/salesperson/date sent/overdue), sorting, and risk highlighting. Quotation-level risk logic (`src/lib/quotationRisk.ts`) mirrors lead risk: overdue follow-up, missing next action, and staleness (no activity in 10+ days) are all derived, not stored; "Follow-up Due" is a computed display status layered on top of the existing `SENT`/`FOLLOWED_UP` enum values, not a new stored status. Added `nextAction`, `wonAt`, `lostAt`, `lostReason` to `Quotation`. Working actions: mark sent, schedule follow-up, change status, add note, mark Won, mark Lost (mandatory reason) — every quotation action also writes to the linked Lead's activity timeline, since Quotation has no activity log of its own.

The dashboard (`/`) was rebuilt around money and action: 8 stat cards, a prominent **Money at Risk** section (overdue quotation value, uncontacted-lead value, missing-next-action value, stale-quotation value, plus a deduped total), an **Attention Required** feed combining the most urgent leads and quotations ranked by severity and value, and a **Team Snapshot** table per salesperson. All numbers are computed live from the database via `src/server/data/metrics.ts` — nothing is hardcoded.

Known simplification: the "Money at Risk" total dedupes *within* the lead-side and quotation-side risk buckets, but a lead and its own quotation can both still contribute if both are independently flagged — this can slightly overstate the total when the same underlying deal is at risk at both stages. Documented in [ARCHITECTURE.md](ARCHITECTURE.md). No Customers view was built this phase (moved to Phase 4 below, per the phase's actual instructions).

## Phase 4 — Customer Intelligence & Repeat-Order Detection ✅ Done

Customers list (`/customers`) and Customer detail (`/customers/[id]`) — the latter deliberately **read-only** (no server actions), since Phase 4's job was surfacing intelligence, not adding another mutation surface. Added `Customer.contactPerson` (the only schema change this phase needed).

Two new rule-based, no-AI signals live in `src/lib/customerIntelligence.ts`: **customer status** (Prospect/Active Customer/Repeat Customer/Dormant/Lost, derived from won/lost/active lead counts and last-touched date — never stored) and the **repeat-order signal** (Normal/Due Soon/Repeat Order Due/Overdue-Dormant, estimated by comparing the average gap between a customer's historical won orders to how long it's been since the last one — requires 2+ won orders to be eligible at all). Both are explicitly labeled as estimates, not guarantees, everywhere they're shown.

The customer detail page's chronological timeline merges enquiries, quotations, activities (including cross-posted quotation actions from Phase 3), and won/lost outcomes across every lead the customer has ever had, all linking back to the source lead/quotation. The dashboard gained a **Repeat Revenue Opportunities** section (customers likely due for reorder, with a suggested action) and the existing unified **Attention Required** feed now also surfaces the two most urgent customer signals (overdue-for-reorder, high-value-gone-dormant) alongside lead/quotation items — Money at Risk remains the dashboard's primary concept, per instruction.

Seed data expanded from 6 to 8 customers and from 11 to 21 leads, adding real multi-order purchase history so every customer status and all four repeat-order states have a genuine, verifiable example (Bharat Engineering Corporation: healthy repeat buyer; Ganesh Steel Industries: due soon; Kiran Textile Mills: repeat order due; Vikram Pumps & Fittings: dormant and overdue, the flagship demo case; Deccan Steel Traders: lost).

## Phase 5 — Team Management, Daily Work Queue & Notifications ✅ Done

Three new surfaces, all built to answer "what does each salesperson need to do today, and what's being neglected": the management **Team** page (`/team`, `/team/[id]`), the company-wide **Daily Work Queue** (`/tasks`), and the personal **My Day** view (`/my-day`). `src/lib/taskRisk.ts` adds task-level escalation (Overdue/Due Today/Upcoming/Completed, plus "seriously overdue" at 3+ days) to the existing lead/quotation/customer risk family, and the lead detail page's follow-ups card was refactored to use it instead of its own copy.

Real in-app **notifications** now exist: `Notification` gained `type`, `entityType`, `entityId` (linking back to the relevant lead/quotation/customer) and a DB-level uniqueness constraint per (company, type, entity, recipient) so the generation logic can't create duplicates even when called from multiple places in one request. `syncNotifications` derives notifications from the same risk logic every other page already uses — no separate rules. A header notification bell (unread badge, mark one/all read) and a "Viewing as" user switcher were added; since there's no login yet, the switcher just sets a cookie, isolated behind `src/lib/currentUser.ts` as the one seam to swap for real auth.

The dashboard gained a small, deliberately minimal integration: Today's Work / Overdue Across Team / Team Workload / Unread Notifications quick links, and Team Snapshot rows now link to `/team/[id]`. Money at Risk remains the dashboard's primary concept, per instruction. Seed data expanded to demonstrate an overloaded salesperson (Amit, piled with overdue tasks) alongside team members with clean queues.

## Phase 6 — Authentication, Company Workspaces & Multi-Tenant Permissions ✅ Done

Real local authentication: DB-backed sessions (`Session` model, random token in an httpOnly cookie), scrypt password hashing (`src/server/auth/password.ts`, zero new dependencies — deliberately avoiding native modules like bcrypt given this machine's lack of a C++ toolchain), a `/login` page, and `requireSession()` guarding every route under the new `(app)` route group. `User` gained `passwordHash` and `isActive`.

Company-scoped data isolation is enforced **server-side**, everywhere — not just in the UI. Every data-fetching function and every server action was rewritten to filter by `companyId` at the query itself (`findFirst({ where: { id, companyId } })` instead of `findUnique({ where: { id } })`, or `findFirst({ where: { id, lead: { companyId } } })` for `Quotation`, which has no direct `companyId` column), throwing a `ForbiddenError` — surfaced as a normal "not found" page, never a stack trace or a silent redirect — on any cross-tenant access attempt, including by direct URL manipulation.

Three roles (Owner, Sales Manager, Salesperson) are enforced through small reusable helpers in `src/server/auth/permissions.ts` (`canManageTeam`, `canManageCompany`, `getOwnerScope`, `assertSameCompany`) rather than scattered inline role checks. Salespeople see only their own leads/quotations/tasks/relevant customers on list pages; Owner and Sales Manager see the whole company. `/team` and `/settings/company` are gated at the page level (`<NotAuthorized>`) for roles that shouldn't reach them, and the sidebar nav filters itself by role.

New surfaces: `/settings/company` (Owner-only, editable company name/industry/phone/email/city/state/timezone/currency) and an expanded `/team` with a "Manage Team" card (Owner-only: add a user with a temporary password, change role, activate/deactivate — deactivating immediately deletes that user's sessions, ending them everywhere). `AuditLog` is now actually written to, for six specific events: lead owner change, quotation status change, lead Won/Lost, user created, role changed, user activated/deactivated, and company settings changed — deliberately not a general activity log (that's what `Activity` is for).

A second fully-fictional demo company ("Om Precision Tools & Dies Pvt. Ltd.", Coimbatore — 3 users, 3 customers, 4 products, 5 leads, 2 quotations, 3 tasks) was seeded alongside the original ("Shree Balaji Industrial Equipments"). Isolation was verified by hand in-browser in both directions: logging in as each company's Owner/Manager/Salesperson and attempting direct-URL access to the other company's lead/customer/quotation/team-member records (all correctly return "not found"), confirming list pages never leak a row count or name from the other tenant, confirming a deactivated user cannot log in and loses any existing session immediately, and confirming logout blocks every protected route. All existing Phase 1–5 functionality (dashboard, leads, quotations, customers, tasks, my day, team, notifications, repeat-order signals, money-at-risk) was regression-tested post-auth with no server errors.

The old cookie-based "Viewing as" identity simulation from Phase 5 (`src/lib/currentUser.ts`, the header `UserSwitcher`) was removed entirely and replaced by real session identity throughout.

## Phase 7 — Integrations Foundation & Universal Lead Ingestion ✅ Done

A provider-independent ingestion pipeline so every future lead source — real or not-yet-built — feeds the same funnel through the same path: normalize → validate → detect possible duplicate → create/update customer → create lead → assign (or leave unassigned) → log activity → notify. No connector, including the two that work this phase, ever writes to `Lead`/`Customer` directly; everything funnels through `src/server/ingestion/pipeline.ts`'s `ingestLead()`.

Two new models: `IngestionBatch` (one row per ingestion event — a CSV upload, a manual add, eventually a webhook sync — with received/created/duplicate/invalid counts) and `IngestionRecord` (one row per normalized enquiry, whatever its outcome, linking to the `Lead`/`Customer` it produced). `Integration` gained `enabled`, `lastSyncAt`, `lastSuccessAt`, `lastError`; `IntegrationType` grew to cover all nine listed connectors (added `TRADEINDIA`, `WEBSITE`, `CSV_IMPORT`, `MANUAL`); `IntegrationStatus` grew `COMING_SOON` and `REQUIRES_SETUP` alongside the existing `NOT_CONNECTED`/`CONNECTED`/`ERROR`.

**Manual entry**: a compact inline "+ Add Lead" form on `/leads` (same expand-in-place pattern as Phase 6's Manage Team card, not a separate page) — customer, contact details, source, product/requirement, estimated value, salesperson, priority, and a *required* next action + deadline, since a single deliberate entry can reasonably demand what the core rule needs up front (bulk CSV rows cannot, and are flagged by the existing risk system instead, same as any other lead missing a next action).

**CSV import** (`/leads/import`): Upload → Map → Preview & Validate → Import, backed by a hand-rolled CSV parser (`src/lib/csv.ts` — quoted fields, embedded commas/newlines, ragged rows all handled without crashing; no new dependency) and a synonym-based column auto-mapper (`src/lib/csvMapping.ts`) that never assumes a fixed layout. Preview and validation happen client-side against data the server already returned (existing customer contacts, for duplicate hints); the actual import re-validates and re-checks every row server-side through the same `ingestLead()` path manual entry uses — the client's preview is UX only, never trusted for correctness.

**Duplicate detection** (`src/server/ingestion/duplicates.ts`): two tiers. "Exact" — same source + external lead ID already ingested — is always blocked, no override (only applies to sources with an external ID, so not manual/CSV yet). "Possible" — the matched customer (by normalized phone or email) already has an active lead opened in the last 3 days — is surfaced for a human decision (manual entry: an inline "Possible Duplicate... Create Anyway?" prompt; CSV: the row is flagged and unchecked by default in the preview, but importable if the user opts in). Nothing is ever auto-merged. A pleasant side effect of the sequential per-row `ingestLead()` calls: two rows in the *same* CSV batch that describe the same new customer are caught too, since the second row's duplicate check runs after the first row's lead already exists in the database.

**Integrations page** (`/settings/integrations`, Owner + Sales Manager, same visibility tier as `/team`): a connector grid (IndiaMART/Justdial/ExportersIndia/TradeIndia/WhatsApp/Gmail/Website Forms all "Coming Soon"; CSV Import and Manual Entry "Connected," the only two that function this phase) plus a compact Import History table (source, file, who, received/created/duplicate/invalid counts, when) reading from `IngestionBatch` — built to extend to webhook/API imports later without changing shape.

**Lead source visibility**: a new muted `SourceBadge` (small colored dot + label, deliberately quiet so it never competes with status/priority/risk badges) replaces plain source text on the Leads table and lead detail Overview card.

Tenant isolation extended to the new models the same way as everything else: `IngestionBatch`/`IngestionRecord` are `companyId`-scoped, duplicate detection and customer matching only ever query within the caller's own company, and Company A's import history is invisible to Company B (verified in-browser). Manual add and CSV import were both exercised end to end in the browser (including the duplicate-warning flow); the CSV parser and pipeline were additionally verified directly against quoted/ragged/malformed input and a same-batch duplicate case. All existing Phase 1–6 functionality (dashboard, leads, quotations, customers, tasks, my day, team, auth, multi-tenancy) was regression-tested with no server errors.

## Phase 8 — Real External Integration Foundation ✅ Done

Proves SalesLeak can receive real external enquiries safely, without connecting any live third-party account. One real API route this phase — `POST /api/webhooks/[provider]/[token]` — everything else stays server actions; the route itself just adapts Request/Response to `src/server/ingestion/webhookHandler.ts`, which contains all the actual logic, per the "keep handlers thin" instruction.

**Provider adapter architecture** (`src/server/ingestion/connectors/`): a `ProviderAdapter` interface (`parse()`, `samplePayload()`) so provider-specific field mapping never lives in a route handler. IndiaMART's adapter is built against their documented lead-push field names — never tested against a live account, since no credentials/access were provided; the Integrations page always labels it **Test Mode / Credentials Required**, never Connected, per explicit instruction not to fake a live connection. The Website Forms adapter backs a real public page (`/website-form/[token]`) that doubles as both an embeddable company contact form and the local dev test page — submitting it really does create a real lead, so it's allowed to show **Connected**.

**Webhook security** (`src/server/ingestion/security.ts`): a random 24-byte token is the sole tenant-resolution mechanism (`prisma.integration.findFirst({ webhookToken, type })`) — there is no company id anywhere in the request, so "Company A's token used against Company B" is structurally impossible, not just checked for. HMAC-SHA256 signature verification is applied only when a `signingSecret` is configured (neither IndiaMART nor a browser-submitted form can meaningfully sign a request, so this is conditional, not forced); timestamp-freshness and a per-token in-memory rate limiter (60 req/min, documented as needing Redis to survive multiple instances) are both implemented and wired in. `signingSecret` is shown in plaintext exactly once at generation, masked thereafter; `webhookToken` is shown in full since it's meant to be copied into a URL.

**Idempotency**: exact duplicates (same source + external lead ID already recorded) are blocked unconditionally, reusing Phase 7's duplicate logic as-is — a provider retrying a delivery is a safe no-op. "Possible" duplicates (same customer, very recent open lead) are logged and not created, since a webhook has no human to ask mid-request.

**Failed Ingestion Queue**: malformed JSON, an unparseable payload, or a validation rejection all land in a new `FailedIngestion` row (raw payload, normalized payload if one was produced, error, retry count) — nothing is ever silently discarded. `/settings/integrations` lets an Owner/Manager inspect the raw data, correct the fields `validate.ts` actually requires, retry through the exact same `ingestLead()` pipeline, or dismiss it.

**Integration Test Console**: "Send Test Payload" on IndiaMART and Website Forms builds a realistic sample payload, runs it through the *real* ingestion path (`processProviderPayload()` — the same function the live webhook route calls), and shows the normalized preview plus the created/duplicate/error outcome — no HTTP round trip, no simulation.

**Monitoring**: `Integration` gained `webhookToken`, `signingSecret`, `totalReceived`; `IntegrationStatus` gained `TEST_MODE`. Per-connector cards show records received, last success, last attempt, last error, and a derived health dot (healthy/error/unknown) — deliberately minimal, not a metrics system. "Disabled" is computed from `enabled: false`, never a separately stored status that could drift out of sync.

**Email ingestion preparation** (`src/server/ingestion/connectors/email.ts`, `emailFixtures.ts`): a normalization function and mock payloads only — no route, no Gmail OAuth, not reachable from outside the codebase, exactly as instructed.

Tested end to end in-browser and via direct HTTP: a realistic IndiaMART payload through webhook → normalize → duplicate-check → customer → lead → activity → notification; the public website form creating a real lead; a duplicate submission correctly creating zero new leads (idempotent); a malformed (non-JSON) and a field-incomplete payload both correctly landing in the Failed Ingestion Queue instead of failing silently; a queued failure corrected and retried into a real lead; Company 1's webhook token verified to only ever affect Company 1 regardless of which company's session is active in the browser; an unknown token and a GET request both safely rejected (404 / 405). All existing Phase 1–7 functionality (dashboard, leads, quotations, customers, tasks, my day, team, auth, multi-tenancy, CSV import, manual entry) was regression-tested with no server errors.

## Phase 9 — AI Intelligence Layer ✅ Done

A provider-abstracted AI service so SalesLeak can use AI to speed up real work — never as a chatbot, never as something that acts on its own. The deterministic risk logic from Phases 1–5 (`src/lib/leadRisk.ts` etc.) remains the sole source of truth for every status/badge/dashboard figure; AI only ever adds an advisory layer beside it.

**Provider abstraction** (`src/server/ai/`): a small `AIProvider` interface (`isConfigured()`, `generateJSON()`) with one real implementation, `AnthropicProvider` (`providers/anthropic.ts`, plain `fetch` against the Messages API — no SDK dependency for one HTTP call). `generateStructured()` in `client.ts` is the single entry point every feature uses: if no provider is configured, a feature's own deterministic `mockResult()` runs immediately (development mode, always clearly labeled, never disguised as real); if a provider is configured, a real call is attempted with a timeout, JSON extraction, and schema validation (`schema.ts` — a small dependency-free validator), and *any* failure — timeout, malformed JSON, a schema mismatch, an API error — returns an honest `{ ok: false }` rather than silently substituting mock data. Every call, mocked or real, success or failure, writes one `AiUsageLog` row.

**Enquiry Extraction**: paste messy text into the Add Lead form ("hi sir ravi this side need 5 ton gp material...") and AI pre-fills customer name, phone, quantity, and other fields it can confidently identify — never inventing what isn't there (unmentioned fields stay null). The extraction only ever pre-fills already-editable form fields; the user reviews and can change anything before "Add Lead" saves it through the unchanged Phase 7 `createManualLead` pipeline — human approval is the review-and-submit step itself, not a separate confirmation dialog.

**Lead Insights, Customer Summary, AI Sales Brief**: three surfaces, all backed by one new `AiInsight` model — a cached row per (company, kind, entity) with a cheap `sourceVersion` fingerprint, so a repeat page view never re-spends an AI call on unchanged data; a manual Regenerate button always forces a fresh one. Lead Insights (on Lead Detail) bundles a short summary, an advisory priority signal (High potential / Medium potential / Low information / Urgent attention, always with a one-sentence reason) and a suggested next action into a single generation — one AI call instead of three, since all three concern the same lead context. Customer Summary (Customer Detail) and the AI Sales Brief (Dashboard, next to Money at Risk, never replacing it) follow the same cached-and-labeled pattern.

**The one place an AI suggestion can become a real change**: clicking "Approve & Schedule" on a Lead Insights next-action suggestion calls the *existing* `scheduleFollowUp()` server action from Phase 2 unchanged — creating a real Task, attributed to the human who clicked approve. AI never calls this itself. Nothing in Phase 9 gives AI the ability to set pricing, send a quotation or message, mark Won/Lost, reassign a salesperson, merge customers, or delete anything.

**Cost control**: the `sourceVersion` cache avoids redundant calls; prompts send only small, purpose-built digests (a dozen whitelisted fields, never a raw Prisma row or `{...lead}` spread) rather than dumping database rows at the model; `AiUsageLog` tracks provider/mocked/success/latency per call, no billing math attempted.

**Ingestion enrichment** (`src/server/ai/features/enrichIngestion.ts`): a hook wired into `ingestLead()` that can fill *only* missing structured fields from a source's free text using the same extraction feature — off by default (`AI_INGESTION_ENRICHMENT` env flag), architecture prep for a future connector that arrives as mostly free text, never overriding a field a provider already supplied.

Tested end to end in mock mode (no `ANTHROPIC_API_KEY` configured in this environment, so every AI surface exercised was the development-mode path): messy-text extraction → pre-filled form → edited → saved as a valid lead; Lead Insights generated, cached, and correctly re-served on reload; "Approve & Schedule" creating a real Task and Activity (which correctly cleared the lead's "untouched" risk flag as a side effect, with no special-casing needed); Customer Summary and AI Sales Brief generating from real company data with correct numbers; a fake-but-configured API key exercised the honest real-provider-failure path end to end (401 → `{ok:false}`, logged to `AiUsageLog`, mock data never substituted); malformed/non-JSON model output safely rejected by `extractJson`/`validateObject` without throwing; full cross-tenant isolation confirmed (Company 1 and Company 2 each generate independent, non-leaking AI content). All existing Phase 1–8 functionality was regression-tested with no server errors. One bug found and fixed during testing: the customer-summary mock template had a grammar defect ("is a active customer customer") from a redundant word plus wrong article — fixed.

## Phase 10 — Pilot-Customer Readiness ✅ Done

Makes SalesLeak usable by a real small B2B company locally, without the team hand-holding it through setup. No new business domain concepts — this phase is entirely about onboarding, configurability, data-quality visibility, findability, and resilience around everything Phases 1–9 already built.

**Signup + Onboarding**: a public `/signup` page creates a brand-new `Company` (`onboardedAt: null`) and its first `User` (`OWNER`), seeds the company's default `Integration` rows from the same `CONNECTOR_CATALOG` seed.ts uses (via a new `getDefaultIntegrationRows()` helper, so a fresh signup and a fresh demo company never disagree), and signs the owner straight into a 7-step wizard at `/onboarding`: company details, add sales team (wraps the existing `createTeamUser` action with a generated temporary password shown once), sales workflow basics, lead sources used, follow-up defaults, bring-in-your-leads (CSV import / manual / skip), and finish. Every step but company details is skippable. The `(app)` layout redirects any Owner whose company has no `onboardedAt` straight to `/onboarding` — so it can't be bypassed by just navigating to `/` — while every other role is unaffected, since an Owner is always the one who completes it.

**Sales workflow settings**: seven new fields on `Company` (`onboardedAt`, `highValueThreshold`, `staleQuotationDays`, `defaultFollowUpDays`, `defaultPriority`, `lostReasonPresets`, `activeLeadSources` — the last two JSON-string arrays, SQLite having no native array type) replace what were previously hardcoded constants in `src/lib/leadRisk.ts` and `src/lib/quotationRisk.ts`. Both risk functions take the threshold as an *optional* parameter defaulting to the old hardcoded value, so no existing call site broke; `src/server/data/companySettings.ts` provides one `getCompanyRiskThresholds()` helper that `leads.ts`/`quotations.ts`/`customers.ts` all now call before computing risk, so a company's own configured thresholds are what its Leads/Quotations/Customers/Dashboard/Health pages actually use. `CompanySettingsForm` on `/settings/company` grew a "Sales workflow" section for all of it; `AddLeadCard` now defaults priority and deadline from company settings; `CloseDealCard` (both lead and quotation variants) offers the company's lost-reason presets as one-click chips beside the existing free-text field. Deliberately **not** built: a configurable "default lead status" — `NEW` is the only sensible starting point for the funnel, and making it a fake setting would add a control with no real effect.

**Sales Process Health** (`/health`, Owner + Sales Manager): a business-health page, not a server-health page. `src/server/data/health.ts` reuses `getLeadsForCompany`/`getQuotationsForCompany`/`getCustomersForCompany`/`getFailedIngestions` — never a new bespoke query duplicating risk logic — to surface seven checks with real counts and links to the actual records: unassigned leads, leads without a next action, leads without a deadline, quotations without a follow-up scheduled, customers with incomplete contact info, possible duplicate customer records (sharing a normalized phone or email — reusing `src/lib/contactMatch.ts`), and failed ingestions. Zero issues renders real zeros with a reassuring banner, never a fake "all good" without the underlying counts.

**Global search**: header-mounted, Ctrl/Cmd+K to focus, Escape to close, arrow keys plus Enter to navigate. `globalSearch()` (`src/server/actions/search.ts`) is a single tenant-scoped server action querying customers/leads/quotations by name, company name, phone, email, or quotation number (leads and quotations also match through their customer's contact fields via a nested Prisma `OR`), debounced 250ms client-side, grouped results in a dropdown.

**Reliability**: an `(app)/error.tsx` (keeps the sidebar/header shell, friendly message, Try Again + back-to-Dashboard) and a root `error.tsx`/`not-found.tsx` pair for anything outside the authenticated shell — no stack trace or database internals ever reaches the UI. The Leads/Customers/Quotations empty states (no filters applied) gained real next-step CTAs — "Import CSV" / "Configure a lead source" / "Go to Leads" — instead of just a passive sentence; every other empty state reviewed (My Day, Tasks, Team, Integrations, AI surfaces) was already genuinely useful and left alone.

**Audit log completeness**: `AuditLog` entries added for the five integration/import actions that didn't have one — webhook configured, signing secret regenerated, integration enabled/disabled toggled, failed ingestion retried, failed ingestion dismissed, and CSV import batch completed — alongside the lead/quotation/user/company-settings coverage Phase 6 already had. Trivial UI clicks (opening a card, a filter change) are still deliberately not audited.

**Demo data reset**: `resetDemoData()` (`src/server/actions/dev.ts`) is hard-gated on `process.env.NODE_ENV !== "production"` — checked in the action itself, not just hidden in the UI, so it's unreachable even if a bad actor got Owner access in a deployed environment — Owner-only, requires typing "RESET DEMO DATA" exactly, and spawns `npx prisma db seed` as a child process rather than refactoring the large standalone `seed.ts` into an importable module. Since reseeding wipes the `Session` table along with everything else, the action destroys the caller's own session and redirects to `/login` afterward, mirroring `logout()`'s established pattern of calling `redirect()` outside any try/catch. The section only renders on `/settings/company` when `NODE_ENV !== "production"`.

Tested end to end in-browser: full signup → 7-step onboarding (including adding a teammate and picking lead sources) → landed on an honestly-empty `/leads` → added a lead with company-default priority/deadline pre-filled → workflow settings visibly wired into `/settings/company`, `AddLeadCard`, and `CloseDealCard`'s lost-reason chips → `/health` correctly flagging the unassigned lead and the contact-incomplete customer it created, with real per-company counts. Security regression re-confirmed post-changes: a company-1 lead ID opened while logged into company 2 correctly 404s with no data leak; `/health` and `/settings/company` correctly reject a Salesperson session server-side (not just hidden nav); global search for a company-1-only customer name returns nothing while logged into a different company. Phase 8's IndiaMART webhook test console re-verified working unchanged (test payload → real lead created → history logged). `npx tsc --noEmit`, `npm run lint`, and `npm run build` all pass clean.

## Phase 11 — Production Readiness ✅ Done

Moves SalesLeak from "works on my machine" to a real, reachable staging deployment on real infrastructure — PostgreSQL instead of SQLite, a Vercel deployment instead of `next dev`, and the security/ops posture a pilot customer's real traffic actually needs. No new business features; this phase is entirely about the ground underneath Phases 1–10.

**PostgreSQL migration**: `prisma/schema.prisma`'s datasource switched from `sqlite` to `postgresql`; `@prisma/adapter-libsql` replaced with `@prisma/adapter-pg` + `pg` (pure-JS, no native build step — this machine still has no C++ toolchain, same constraint noted in Phase 1). The old SQLite migration history was deleted (incompatible dialect, preserved in earlier git history) and replaced with a fresh baseline migration generated directly against a real Supabase database. **Pooled-vs-direct connection split**: the installed Prisma 7.9.1 CLI's `prisma.config.ts` only supports a single `url` (no `directUrl` field, despite some docs suggesting otherwise — verified directly against the installed `@prisma/config` package's types and a live schema-validation error), and `schema.prisma` itself now hard-rejects `url`/`directUrl` in the datasource block entirely. So the split is done by hand: `prisma.config.ts`'s one `url` always points at the **direct** connection (for `migrate`/`db seed`, since a transaction-mode pooler can't run migrations' prepared statements), while the running app's own driver adapter (`src/lib/prisma.ts`) reads `DATABASE_URL` — the **pooled** connection — directly from `process.env`, completely independent of the CLI config.

**Environment & startup validation**: `src/lib/env.ts`'s `validateEnv()` checks `DATABASE_URL` is present and looks like a Postgres URL, called from `src/instrumentation.ts`'s `register()` — which only runs when a server instance actually starts, never during `next build`. This was a real, hit-during-development bug avoided: an earlier version threw eagerly inside `src/lib/prisma.ts` at module scope, which broke `next build` itself (Next.js's "collecting page data" step imports and partially evaluates route modules for pages like `/login` that query the database, even before any real request occurs) — moved the check to `instrumentation.ts` instead, which crashes loudly in production if misconfigured but never touches the build.

**Auth hardening**: in-memory rate limiting added to `login()` (8 attempts / 5 min, keyed by email) and `signup()` (5 / hour, keyed by IP via a new `getClientIp()` helper) in `src/server/actions/auth.ts`, reusing a generalized version of Phase 8's webhook rate limiter (extracted to `src/lib/rateLimit.ts`, since it was already a pure keyed-window utility with no ingestion-specific logic). Everything else reviewed and found already correct from Phase 6: scrypt password hashing, httpOnly/secure(-in-production)/sameSite=lax session cookies, 30-day DB-backed expiry, disabled-user rejection, generic "Invalid email or password" (never reveals which field was wrong), and the existing `findFirst({id, companyId})` tenant-isolation pattern everywhere.

**Structured logging**: `src/lib/logger.ts` — plain JSON lines to stdout/stderr (Vercel captures these automatically; no paid monitoring service added), with a defensive key-based redaction pass and category-specific helpers (`authFailure`, `databaseFailure`, `ingestionFailure`, `webhookFailure`, `aiFailure`, `serverError`). Wired into the actual *handled* failure paths that would otherwise be invisible (a caught-and-swallowed `AiUsageLog` write failure, webhook rate-limit/token/signature rejections, ingestion parse failures) plus a catch-all via `instrumentation.ts`'s `onRequestError` for anything uncaught. Verified working end to end against the real deployment: a real error thrown during regression testing (see below) showed up in `vercel logs` with the exact structured JSON line, full context, no secrets.

**Production safety**: reviewed against the explicit "must be impossible in production" list — `resetDemoData()`'s `NODE_ENV === "production"` guard (Phase 10) and `/login`'s demo-account visibility gate were already correct and needed no changes; confirmed there are zero `NEXT_PUBLIC_*` variables anywhere in the codebase (nothing to accidentally leak to the client bundle); both `error.tsx` boundaries confirmed to only ever render `error.digest`, never `error.message` or a stack.

**Security headers** (`next.config.ts`): a non-nonce Content-Security-Policy (nonces would force every page to dynamic rendering for no real benefit here), `X-Content-Type-Options: nosniff`, `Referrer-Policy: origin-when-cross-origin`, `Permissions-Policy` disabling camera/mic/geolocation, and `frame-ancestors 'self'` — carved out via a negative-lookahead path pattern so the deliberately-embeddable `/website-form/[token]` page (meant to be iframed into a company's own external site, per Phase 8) doesn't inherit a policy that would break its one job.

**`GET /api/health`**: app-plus-database liveness only (`SELECT 1`) — no credentials, env vars, or customer data in the response, ever.

**Seed/migration separation**: `seed.ts` now refuses to run at all when `NODE_ENV=production` (hard-coded check, independent of whoever's running the command); `package.json` gained explicit `db:migrate:dev` / `db:migrate:deploy` / `db:seed` / `postinstall` (`prisma generate`) scripts so the two paths — schema migration vs. fictional demo data — are named separately and share no code.

**Git + deployment hygiene**: initialized git (previously ungitignored, all Phase 1–10 work at risk of loss), `.gitignore` audited (`.env*` with a `!.env.example` exception, local agent/editor tooling excluded), `.env.example` documents every variable. A real gap found and fixed during Vercel deployment: `vercel deploy` does **not** reliably respect `.gitignore` for `.env` files — the first deployment uploaded the real local `.env` (Vercel only warns, doesn't refuse) — fixed with an explicit `.vercelignore`, verified by redeploying and watching the upload drop from 3.1MB to 435B with no warning.

**Vercel deployment**: a dedicated project (`salesleak`, deployed via CLI directly from the local filesystem — no GitHub repository connected or touched, per instruction) with `DATABASE_URL`/`DIRECT_URL`/`APP_URL` configured as sensitive production environment variables. `ANTHROPIC_API_KEY` deliberately left unset (no paid AI usage on a staging deployment nobody's paying to use yet) — confirmed the app runs identically either way.
